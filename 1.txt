python -m uvicorn server.app:app --reload --port 8000main.py: מנהל את התפריט ואת סדר הפעולות.


config.py: טוען את כתובת השרת מתוך .env.
input_helpers.py: קבלת קלט ובדיקתו באמצעות Questionary.
api.py: שליחת בקשות HTTP וקבלת התשובות.
output.py: הצגת התוצאות למשתמש.
.env: הגדרות כתובת שרת הפייתון.

main.py: הגדרת ה־Endpoints וקישור שלהם לפונקציות המתאימות.
database.py: הגדרות החיבור למסד באמצעות Peewee.
service.py: השאילתות והחישובים. כאן יהיה עיקר השינוי בלוגיקה במבחן.
auth.py: רישום משתמשים, גיבוב סיסמאות ובדיקת התחברות, כנדרש בחלק השני.
schemas.py: הגדרת מבנה בקשות שמגיעות לשרת, אם נשתמש בכך.
.env: שם המסד ופרטי ההתחברות אליו.

SQL/schema.sql: פקודות ליצירת הטבלאות החדשות שתידרש לתכנן.
SQL/design.txt: הסבר על הטבלאות והקשרים, כפי שנדרש במבחנים.
requirements.txt: הספריות להתקנה.



client/.env: משנים את SERVER_URL רק אם כתובת שרת הפייתון או הפורט שלו משתנים.

client/config.py: אין צורך לשנות; שינוי בשם ה־DB נעשה ב־server/.env בלבד.

client/input.py
 אחראי לקבלת קלט ולבדיקתו. לרוב אין צורך לשנות את הפונקציות.
ב-main.py בוחרים את שדה החיפוש ואת השאלה; אם מחפשים לפי שדה יחיד, מדלגים על choose_search וקוראים ישירות ל-read_id או ל-read_text.
    validate_id: בודקת שהמזהה הוא מספר שלם חיובי.
    validate_text: בודקת שהטקסט אינו ריק.
    choose_search: מציגה בחירה בין מזהה לשדה נוסף.
    read_id: מקבלת מזהה ומחזירה מספר.
    read_text: מקבלת טקסט ומחזירה אותו בלי רווחים בקצוות.

client/api.py שולח בקשות לשרת
    get_data לקבלת נתונים ו-
    post_data לשליחת גוף JSON.
    במבחן מתאימים בקריאה את ה-endpoint ואת שמות הפרמטרים לשרת; לרוב אין שינוי בקוד הפונקציות עצמן.


client/output.py מציג את תשובת השרת. במבחן משנים את הכותרות ואת המפתחות בתוך result לפי השדות שהשרת מחזיר.
שדות שמופיעים רק במצב מסוים מדפיסים בתוך if; הקובץ אינו מבצע שאילתות או חישובים.

server/database.py מכין את החיבור למסד באמצעות ההגדרות שב-server/.env; בדרך כלל אין צורך לשנות בו קוד.
אחרי ייבוא הנתונים מעדכנים ב-server/.env את DB_NAME לשם המסד בפועל ומפעילים מחדש את שרת הפייתון.

server/service.py מכיל את השאילתה והלוגיקה: חיפוש, JOIN, סינון, חישוב ומיון.
במבחן מתאימים את ה-SQL ואת מילון התוצאה; סדר row[0], row[1] וכו' חייב להתאים לסדר השדות ב-SELECT.

    איך השאילתה עובדת?

    SELECT: בוחר את השדות שנחזיר.
    AS d,‏ AS ds,‏ AS s: נותנים שמות קצרים לטבלאות בתוך השאילתה.
    JOIN: מחבר ציוד, מצב ציוד ותחנות לפי המזהים.
    WHERE: מסנן לפי הקלט ולפי תחנות פעילות.
    ds.total_units > 0: מונע חלוקה באפס.
    ORDER BY ... ASC: מסדר מהכשירות הנמוכה לגבוהה.
    LIMIT 1: מחזיר רק את התוצאה הראשונה.
    זה הקובץ שבו מתאימים:

    את שדות החיפוש ב־condition.
    את שמות הטבלאות והקשרים ב־JOIN.
    את השדות, החישוב והסינון.
    את המיון: ASC לקטן ביותר, DESC לגדול ביותר.
    את המילון המוחזר, בהתאם לסדר השדות ב־SELECT ולתצוגה ב־client/output.py.

server/main.py מגדיר את ה-Endpoints, בודק את פרטי הבקשה וקורא לפונקציות שב-service.py.
במבחן מתאימים את הנתיב ושמות הפרמטרים לבקשת הלקוח; את השאילתות והחישובים משנים ב-service.py.
    מה לשנות ב-server/main.py במבחן:

    1. "/devices/lowest-readiness"
    להחליף לנתיב שנדרש בשאלה. אותו נתיב חייב להופיע בבקשת הלקוח.
    2. device_id ו-device_name
    להחליף בכל הפונקציה לשמות הפרמטרים שנדרשים.
    לדוגמה: book_id ו-isbn. השמות חייבים להתאים למפתחות params שהלקוח שולח.
    3. get_lowest_readiness
    זה שם פונקציית ה-Endpoint. לשנות אם נדרש שם אחר; הוא לא קובע את כתובת הבקשה.
    4. find_lowest_readiness
    להחליף בשם פונקציית החיפוש שכתבת ב-service.py.
    לעדכן גם את ה-import בראש הקובץ וגם את שתי הקריאות לפונקציה.
    5. "id" ו-"name" בקריאות לחיפוש
    אלה סוגי החיפוש שמועברים ל-service.py.
    אם משנים למשל "name" ל-"isbn", גם service.py צריך לזהות "isbn".
    6. בדיקות הקלט
    לשני שדות חלופיים משאירים את מבנה if/elif/else.
    לשדה יחיד מסירים את האפשרות השנייה ואת בדיקת "שניהם יחד".
    מתאימים את סוגי הפרמטרים והבדיקות לדרישה.
    7. detail="..."
    מעדכנים את הודעות השגיאה לפי הנושא.
    מוודאים ש-result is None באמת מסמן מצב שבו צריך להחזיר 404.
    מה נשאר בדרך כלל:
    app = FastAPI()
    פונקציית show_tables
    return result

server/schemas.py מגדיר את השדות שהשרת מקבל בגוף בקשת POST.
UserRequest מכילה שם משתמש וסיסמה; ב-InvestigationRequest משנים את שדות החיפוש לפי המבחן ומתאימים אליהם את הלקוח ואת ה-Endpoint.
