מבחן סיום — מערכת תחקור
Full Stack Investigation System
מטרת הבחינה
לצה״ל קיים בנק מטרות הכולל מידע על מטרות, רמת מסוכנות והמיקום האחרון הידוע שלהן. בנוסף קיימים אמצעי תקיפה כגון מטוסים, כטב״מים, תותחים וטילים. מטרת המערכת היא לאפשר תחקור והפקת מידע ממאגרי הנתונים האלה.
בבחינה תבנו אפליקציה מלאה הכוללת לקוח, שרת ומסד נתונים טבלאי.
Python Client
    ↓ HTTP
Python Server (FastAPI / Flask)
    ↓
Relational Database (MySQL / SQLite / PostgreSQL)

במקומות שבהם נדרשת עבודה מול ה־Database ניתן לבחור בין ORM לבין Connector והרצת SQL, אלא אם נאמר אחרת.
מה נבדק
• קוד תקין ו־Flow מלא בין Client, Server ו־Database.
• Clean Code — שמות ברורים, פונקציות קצרות ומבנה קריא.
• SRP — אחריות ברורה לכל פונקציה וקובץ.
• DRY — ללא שכפול לוגיקה מיותר.
הסברים ודוגמאות מפורטים נמצאים בנספחי ה־PDF. בנספחים יש גם דוגמאות שימוש בספריות הרלוונטיות.
נהלים
• אין שימוש ב־AI בשום מצב.
• אין חיפוש כללי בגוגל.
• מותר להשתמש בתיעוד רשמי של חבילות ובאתרים לימודיים כגון W3Schools.
• יש לבטל AI בעורך הקוד.
• אין לפתוח דוגמאות קוד מפרויקטים או תרגילים קודמים.
אי הקפדה על הנהלים עלולה להוביל לפסילת הבחינה.





Feature 1 — Last Known Location
השאלה שעל המערכת לענות עליה:
מה שם המקום האחרון שבו נצפתה מטרה מסוימת? ניתן לחפש לפי id או לפי name של המטרה.
Database — מבנה הטבלאות הקיימות:

Location table:
Field	Meaning
id	Primary Key
name	Location name (str)
lat	Latitude (float)
long	Longitude (float)
country	Country (str)
description	Description (str)


Targets table:
Field	Meaning
id	Primary Key
name	Target name (str)
organization	Organization (str)
danger_level	1-10
rank	Rank (str)
last_known_location_id	FK → locations.id


תקבלו נתוני דמה עבור שתי הטבלאות. יש להפעיל את ה־Database ולטעון את הנתונים לפני הרצת המערכת.
עליכם לייבוא את הקבצים שמתאימים לסוג הDB שאתם עובדים איתו: CSV/SQL/DB.

Feature 2 — Strike Asset Investigation
זהו החלק הפתוח.
בחלק זה מצטרף מידע חדש (שאתם צריכים להגדיר עבורו טבלאות) - אמצעי תקיפה, ותקיפה.
אמצעי תקיפה (strike asset) = כלי נשק עם תיאור, חימוש, וכמות דלק מסוימת.
תקיפה (strike) = אמצעי תקיפה + מטרה + מיקום.

עליכם לתכנן ולממש Feature Full Stack שעונה על השאלה:
בהינתן אמצעי תקיפה מסוים, כמה מטרות נתקפו באמצעותו בכל מיקום?
ניתן לחפש את האמצעי לפי id או name.

פ'יצ'ר זה הוא מאובטח - כלומר משתמש צריך שם משתמש וסיסמה תקינים כדי לבצע את השאילתה הזו.
נדרש להוסיף ENDLPOINT לרשום משתמש חדש ולשמור אותו עם הסיסמה שלו בצורה מגובבת (hashed) בתוך קובץ CSV.
המשתמש נדרש לספק את שם המשתמש והסיסמה שלו כחלק מבקשת השאילתא מהלקוח.


המידע שצריך להישמר
לכל Strike Asset יש לפחות:
id
name
armament
max_fuel



לכל Strike יש לפחות:
date
target
strike_asset
location
result  # missed | injured | dead

ניתן להניח שכל מטרה נתקפת על ידי אותו אמצעי באותו מיקום - פעם אחת בלבד
חשבו על הטבלאות שעליכם לייצר על מנת שהישויות יהיו בעלות התכונות המתוארות, ובנוסף - שיהיה אפשר לבצע את השאילתה.


Client — Feature 2
• הוסיפו אפשרויות רלוונטיות לתפריט על מנת לבצע את השאילתה.
• אפשרו יצירת משתמש חדש באמצעות username ו־password.
• אפשרו חיפוש Strike Asset לפי id או name.
• קבלו username ו־password לפני ביצוע התחקור המאובטח - ולידציה שאינם ריקים.
• שלחו Request לשרת והציגו את התוצאה בצורה קריאה, לא בהדפסה ישירה של JSON.
אתם מחליטים אילו פונקציות, קבצים ותיקיות להוסיף, תוך שמירה על Clean Code, SRP ו־DRY.

Server — Feature 2
• צרו Endpoint ליצירת משתמש חדש.
• שמרו משתמשים בקובץ users.csv במבנה username,password_hash.
• הסיסמה חייבת להישמר כ־hash, לדוגמה באמצעות bcrypt.
• צרו Endpoint מאובטח לתחקור Strike Asset.
• ה־Endpoint מקבל strike asset id או name יחד עם username ו־password.
• אם האימות נכשל — אין להריץ את התחקור ואין להחזיר מידע מה־Database.
• אם האימות הצליח — תחקרו את ה־Database והחזירו לכל location את מספר המטרות הייחודיות שנתקפו באמצעות האמצעי.
יש להחזיר location name ולא location_id.

Database Design — Feature 2
תכננו את הטבלאות הדרושות כדי לבצע את השאילתה
צרו sql/design.txt ובו:
• שמות הטבלאות החדשות.
• השדות וסוגי הנתונים.
• Primary Keys.
• Foreign Keys והטבלאות שאליהן הם מצביעים.
• הסבר קצר למה המבנה שבחרתם מאפשר לענות על שאלת התחקור.

בסיום הבחינה
• Feature 1: חיפוש Target לפי id או name והצגת last known location.
• Feature 2: חיפוש Strike Asset לפי id או name, Authentication, והצגת מספר מטרות ייחודיות שנתקפו בכל location.
• Client ו־Server צריכים להיות תואמים ב־Endpoint, HTTP Method ומבנה Request/Response.
• המערכת תיבדק כיחידה אחת: Client → Server → Database → Server → Client.
